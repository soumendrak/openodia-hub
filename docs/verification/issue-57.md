# Issue #57 verification

## Implemented scope

The explicit inventory contains 46 UI strings: navigation and language/control labels, home hero/opening/statistics and footer. English and Odia render through the existing provider; localized sections carry the selected language while untranslated page bodies remain marked English. The public `/translation-status` page and `/api/translation-status` distinguish translation presence from exact-wording native review. The API is documented in OpenAPI and discovery.

New English keys require a tracking entry and an explicit Odia translation or blank placeholder. Unknown keys, missing placeholders, invalid Odia wording and mismatched interpolation tokens fail the locale CLI/CI gate. Tracked placeholders remain visibly missing, not translated; their UI controls fall back to readable English instead of rendering blank. The contributor path supports a single string and direct GitHub edits.

The trusted native-review publisher reads GitHub API metadata without checking out PR application code, executing notification artifacts, or trusting a contributor-controlled workflow result. `pull_request_target`, `issue_comment`, and default-branch `workflow_run` events discover PRs through the canonical API. A separate `pull_request_review` workflow has `permissions: {}` and only signals that review metadata changed. It does not decide native approval. The publisher posts `native-review` pending and then success/failure as a commit status on the freshly fetched PR head SHA; its automatic job has a different name. An issue-comment approval therefore updates the correct PR commit even though that event's automatic job runs on the default branch. A contributor-controlled successful job cannot substitute for the trusted status: GitHub requires both a status and check when their names coincide. See [event requirements](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows) and [required-status behavior](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks).

The publisher adds `needs-native-speaker-review` and requires actual configured review of the current commit. Stale, outsider, dismissed and revoked approvals do not count. Formal reviews and explicit SHA-bound comments share one per-reviewer chronology: the latest decision wins, with rejection winning equal-time conflicts. Dismissals use `review_dismissed.created_at`, joined by `dismissed_review.review_id`, rather than the original review submission date. Unknown approval chronology cannot authorize review; unknown dismissal chronology blocks approval. Per-PR matrix concurrency and fresh-head guards before label/status updates prevent stale runs from authorizing a newer head. Renamed locale paths remain protected; reverting all protected-file changes clears the label and succeeds only for the unchanged current head. Only a missing-label 404 is ignored; other API failures report an error status.

Review-run PR associations are candidate numbers, not proof of the head. Discovery verifies open state, base repository, current head SHA, source repository and branch against canonical run metadata. Fork runs may expose no PR associations, and a base-repository commit lookup may also return none; paginated open-PR lookup by fork owner/branch resolves that case. Notification outcomes never provide approval. A configured native reviewer sharing the agent PR author's account can give an explicit SHA-bound review comment after reviewing wording; ownership alone is insufficient. Exact wording, reviewer and date are recorded separately in `ODIA_REVIEWS`.
