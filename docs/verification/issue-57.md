# Issue #57 verification

## Implemented scope

The explicit inventory contains 46 UI strings: navigation and language/control labels, home hero/opening/statistics and footer. English and Odia render through the existing provider; localized sections carry the selected language while untranslated page bodies remain marked English. The public `/translation-status` page and `/api/translation-status` distinguish translation presence from exact-wording native review. The API is documented in OpenAPI and discovery.

New English keys require a tracking entry and an explicit Odia translation or blank placeholder. Unknown keys, missing placeholders, invalid Odia wording and mismatched interpolation tokens fail the locale CLI/CI gate. Tracked placeholders remain visibly missing, not translated; their UI controls fall back to readable English instead of rendering blank. The contributor path supports a single string and direct GitHub edits.

The native-review workflow reads GitHub API metadata without checking out or executing application code with write permissions. It adds `needs-native-speaker-review` and requires an actual configured native review of the current commit. Stale, outsider, dismissed and revoked approvals do not count. Formal reviews and explicit SHA-bound comments share one per-reviewer chronology: the latest decision wins, with rejection winning equal-time conflicts. Dismissals use the GitHub timeline’s `review_dismissed.created_at`, joined by `dismissed_review.review_id`, rather than the original review submission date. Unknown approval chronology cannot authorize review; unknown dismissal chronology blocks approval. Per-PR concurrency, fresh-head reads before evaluation and label mutation, renamed locale paths and edited revocations prevent obsolete runs from clearing a newer head's review requirement. Fork review events evaluate approval with their read-only token and perform no label writes; trusted base-branch target/comment events manage the label. Reverting all protected-file changes removes the stale label only with a trusted token and an unchanged current head. After a formal review on a fork, a PR conversation comment triggers the base workflow to refresh the label once the workflow is on main. A configured native reviewer using the same account that authored an agent PR can give an explicit SHA-bound review comment; ownership alone is not approval. Exact wording, reviewer and date are recorded separately in `ODIA_REVIEWS`.
