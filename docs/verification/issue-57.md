# Issue #57 verification

## Implemented scope

The explicit inventory contains 46 UI strings: navigation and language/control labels, home hero/opening/statistics and footer. English and Odia render through the existing provider; localized sections carry the selected language while untranslated page bodies remain marked English. The public `/translation-status` page and `/api/translation-status` distinguish translation presence from exact-wording native review. The API is documented in OpenAPI and discovery.

New English keys require a tracking entry and an explicit Odia translation or blank placeholder. Unknown keys, missing placeholders, invalid Odia wording and mismatched interpolation tokens fail the locale CLI/CI gate. Tracked placeholders remain visibly missing, not translated; their UI controls fall back to readable English instead of rendering blank. The contributor path supports a single string and direct GitHub edits.

The trusted native-review publisher reads GitHub API metadata without checking out PR application code, executing notification artifacts, or trusting a contributor-controlled workflow result. `pull_request_target`, `issue_comment`, and default-branch `workflow_run` events discover PRs through the canonical API. A separate `pull_request_review` workflow has `permissions: {}` and only signals that review metadata changed. It does not decide native approval. Default-branch scheduled and manual reconciliation independently discover all open PRs, so a contributor removing or suppressing that notification cannot prevent later reevaluation. Manual default-branch rechecks post `native-review` pending and then success/failure as a commit status on the freshly fetched PR head SHA; automatic events publish changed final decisions after recomputing current evidence. The automatic publisher job has a different name. An issue-comment approval therefore updates the correct PR commit even though that event's automatic job runs on the default branch. A contributor-controlled successful job cannot substitute for the trusted status: GitHub requires both a status and check when their names coincide. See [event requirements](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows) and [required-status behavior](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks).

The publisher adds `needs-native-speaker-review` and requires actual configured review of the current commit. Stale, outsider, dismissed and revoked approvals do not count. Formal reviews and explicit SHA-bound comments share one per-reviewer chronology: the latest decision wins, with rejection winning equal-time conflicts. Dismissals use `review_dismissed.created_at`, joined by `dismissed_review.review_id`, rather than the original review submission date. Unknown approval chronology cannot authorize review; unknown dismissal chronology blocks approval. Per-PR matrix concurrency and fresh-head guards before label/status updates prevent stale runs from authorizing a newer head. Renamed locale paths remain protected; reverting all protected-file changes clears the label and succeeds only for the unchanged current head. Only a missing-label 404 is ignored; other API failures report an error status.

Review-run PR associations are candidate numbers, not immutable proof of the triggering head: [old run 38293742421](https://github.com/soumendrak/openodia-hub/actions/runs/38293742421) retained its older source `head_sha` while its associated `pull_requests[].head.sha` refreshed to the PR's newer head. Discovery verifies open state, base repository, source repository and branch against canonical run metadata. It accepts a run SHA matching the fresh PR source head, or the fresh `merge_commit_sha` only after the canonical commit's two parents match the fresh source and base SHAs. This rejects stale source runs and stale merge metadata. `pull_request_review`'s `GITHUB_SHA` is a test-merge commit, while observed REST workflow-run `head_sha` values were source commits; the workflow does not assume those fields are universally equal. Fork runs may expose no PR associations, and a base-repository commit lookup may also return none; paginated open-PR lookup by fork owner/branch resolves either supported SHA shape. Notification outcomes never provide approval. A configured native reviewer sharing the agent PR author's account can give an explicit SHA-bound review comment after reviewing wording; ownership alone is insufficient. Exact wording, reviewer and date are recorded separately in `ODIA_REVIEWS`.

The reconciliation schedule requests a run every five minutes at an offset from the hour (`2-57/5 * * * *`). It runs from the default branch after installation and re-reads current GitHub review, dismissal and comment metadata even when no notification ran. This is eventual reconciliation, not immediate revocation or a guaranteed five-minute deadline: GitHub can delay or drop scheduled runs and disables public-repository schedules after 60 days without activity. A previously successful status can remain stale until reconciliation finishes. If a review signal was missed, maintainers must run **Native Odia review** manually with the default branch selected (other refs are rejected), then verify the completed `native-review` status on the unchanged PR head and current review state before merging. Relevant configured-reviewer current-SHA approval/revoke comment changes also trigger trusted reevaluation, including editing a command into other text or deleting it. Unrelated comments are ignored; use manual default-branch refresh to request a fresh proof without expressing approval. No webhook, production ruleset or branch-protection setting was changed here. See [GitHub's schedule constraints](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

All nonmanual runs recompute review evidence and reconcile labels, but skip pending statuses and skip unchanged final statuses only when the latest matching status was created by `github-actions[bot]` with the same state and description. Paginated status history is newest first; the latest case-insensitive `native-review` context is selected before checking its creator, so an older trusted status cannot hide a newer outsider or pending status. Old status success never supplies approval. API errors still fail the workflow and attempt to replace a prior success with an error status; repeated equivalent trusted errors avoid duplicate writes when status history remains readable. Normal scheduled missing approval or missing reviewer configuration publishes a blocking failure status without failing the reconciliation job or generating routine failure notifications. Manual runs retain fresh pending/final publication after a fresh-head guard; other automatic events publish changed final results and retain failure semantics. This avoids exhausting [GitHub's 1,000 statuses per SHA/context limit](https://docs.github.com/en/rest/commits/statuses), which unconditional five-minute pending/final writes would reach in about 42 hours.

PR file discovery must be complete before either locale review or no-locale cleanup can succeed. The fresh canonical `changed_files` value must be a safe nonnegative integer no larger than 3,000, matching the paginated response length and its unique, nonempty filenames. Any missing/invalid count, mismatch, duplicate, or capped oversized response fails closed with an attempted exact-head error status and no review-label removal. This follows [GitHub's 3,000-file response cap](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests-files).

Comment relevance is filtered before publisher concurrency and again before status/label writes. The original comment author must be a configured reviewer; the current body or an edited body's previous value must be an exact approval/revoke command for the fresh head. Deleted commands are evaluated through their original body even when a different maintainer deletes them. These payloads only signal relevance: current API reviews/comments still determine approval. All other comments are ignored, and equivalent nonmanual results reuse the latest publisher status after fresh evaluation, so unrelated comments or review notifications cannot exhaust the status context.
